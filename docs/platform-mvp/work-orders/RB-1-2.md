## Goal

A role becomes a bundle: a name, a description, **functions** (the ten keys of the table `roles`), one Core group and
members. A new installation starts with exactly two roles, «Administration» and «Mitglied». An existing installation is
moved to the same state and nobody loses a function. A person's functions (`roles_of`) and groups
(`access_groups_of`) are read from roles, so **no gate changes** and the menu works as it is. RB-3 and RB-4 build the
page on the store this item adds.

**Not in this item:** the Rollen page (RB-3); creating, renaming and deleting roles through a page, the people page
offering roles, the audit rows and safety rules 1, 4 and 5 (RB-4); creating or linking Core groups (RB-4, see rule 9);
data (RB-5); agents (RB-6, RB-7; RB-8 dropped by the founder on 2026-11-21: "Core gateway only"); Probe (RB-9); splitting `admin` (RB-10).

2. **`P/src/identity/roles.py`**, the interface RB-3 and RB-4 build on:

   ```python
   MAX_CLAIM_GROUPS = 32

   class RoleError(Exception)            # every refusal; plain German, safe to show, no name and no address
   class RoleNotFound(RoleError)         # missing, foreign or malformed id: one answer
   class RoleNameTaken(RoleError)
   class UnknownFunction(RoleError)      # not one of the ten keys
   class ProtectedRoleError(RoleError)   # deleting Administration or Mitglied; `admin` outside Administration
   class LastAdministratorError(RoleError)
   class TooManyGroupsError(RoleError)   # a 33rd group in a person's claim

   @dataclass(frozen=True)
   class Role:
       id: UUID; name: str; description: str
       kind: str                          # "administration" | "mitglied" | "custom"
       functions: frozenset[str]
       core_group_id: str | None
       members: frozenset[UUID]           # people; agents come with RB-6/RB-7 in tables of their own

   class RoleStore:
       def __init__(self, conn)
       def list_roles(self) -> list[Role]                 # Administration, Mitglied, then by name
       def get_role(self, role_id) -> Role
       def administration(self) -> Role
       def mitglied(self) -> Role
       def roles_of_user(self, user_id) -> list[Role]
       def create_role(self, *, name, functions=(), description="", core_group_id=None, by=None) -> Role
       def rename_role(self, role_id, *, name, by=None) -> Role
       def set_functions(self, role_id, functions, *, by=None) -> Role
       def set_core_group(self, role_id, core_group_id, *, by=None) -> Role
       def delete_role(self, role_id, *, by=None) -> None
       def add_member(self, role_id, user_id, *, by=None) -> None
       def remove_member(self, role_id, user_id, *, by=None) -> None
   ```

   `by` is the acting person's id. RB-1 stores it as `created_by` / `added_by` and refuses nothing because of it.
   RB-4 uses it for the audit rows (design rule 4) and decides where rule 1 is checked ("a creator adds only functions
   she holds"); the interface stays the same. The frozen file never passes `by` when functions are given (only
   when a role is renamed or deleted, or a member added or removed), so rule 1 can live in the store or on the page.

## Rules

1. **New tables only.** No change to any existing table, column, index, constraint or trigger, to the rows of `roles`,
   or to any existing migration (the frozen file compares the schema before and after). `user_roles` keeps every row
   and is read by nothing after the move: it is the way back for one release. Write in the migration's header and in
   your notes what the way back means: the previous image reads `user_roles` as the move left it, so role changes made
   after the move are not carried back.
2. **Functions are the ten keys of `roles`**, nothing else (`UnknownFunction`, nothing written). **`admin` belongs to
   Administration alone:** Administration always holds it, and no other role may (`ProtectedRoleError`). An
   administrator is therefore exactly a member of Administration. Other functions may be added to Administration.
3. **The two roles.** Exactly one of each kind. Neither can be deleted (`ProtectedRoleError`). The store allows
   renaming them like any role; RB-4 decides whether the page offers it. The kind, not the name, identifies them.
4. **The last administrator.** A change that leaves Administration without an active person (`status = 'active'`) is
   refused with `LastAdministratorError`, nothing changed: `remove_member` and `revoke_role(…, "admin")`. Hold
   Administration's row (`SELECT … FOR UPDATE`) while counting, so two removals at once cannot both pass. Deactivating
   the last administrator through the people page is RB-4's (design rule 3).
5. **Granting oneself a role needs no second person** (founder, 21 November): `add_member` never queues an approval,
   and `by` may be the member.
6. **The 32-group cap** (the Core's `QUERY_MAX_ASSERTED_GROUPS`, design § 2.3). A person's claim groups are the running
   direct grants plus the Core groups of their roles; a group held twice counts once.
   - Every write that can add a group (`add_member`, `set_core_group`, `grant_access_group`, `set_access_groups`)
     checks the result in its own transaction and raises `TooManyGroupsError`, with nothing written, when a person
     would hold more than `MAX_CLAIM_GROUPS`. The message says 32 and names nobody.
   - `PrincipalBroker` raises `TooManyGroupsError` instead of signing more than 32. It never cuts the list.
   - `access_groups_of` returns what is stored, so the people page still shows a person whose grants were stored
     before the cap.
7. **`roles_of` reads roles, and nothing else reads `user_roles`.** No gate, decorator, route or menu changes; the
   console's `allowed_roles` stays. After the change, no SQL in `P/src` outside `identity/migrations/` names the table
   `user_roles` (`builder/team.py` uses the word for a parameter; that stays).
8. **`grant_role` and `revoke_role` keep their meaning**, because `conftest._person`, the first start
   (`bootstrap.ensure_admin`) and the people page still call them:
   - `grant_role(user, "admin")` puts the person into Administration, `"member"` into Mitglied, and any other key into
     the custom role whose functions are exactly that key. That role is created on first use under the function's
     name. An unknown key still raises `UnknownRoleError`.
   - After `revoke_role(user, key)` the person lacks exactly that key and keeps every other function. Leave each
     custom role that grants it, and give back that role's other functions through single-function roles. A key that
     comes from Administration or Mitglied (other than `admin` or `member` themselves) is refused with `RoleError`.
     `revoke_role(…, "admin")` obeys rule 4.
   - `UserRepository.create` puts nobody into a role: an existing test pins that a new account has no roles. The
     console's "Person anlegen" keeps granting `member` (now: Mitglied).
9. **Nothing is written to any tenant.** `RoleStore` takes a connection and no client, and the migration is SQL. RB-1
   only records `core_group_id` (`create_role`, `set_core_group`). RB-4 does all of the following through the client,
   the Core first and the store second, on an administrator's action and never at process start:
   - creating a role's Core group, and renaming it with the role (design § 3);
   - adopting an existing group as a role's group;
   - linking Administration to the tenant's administrator group;
   - creating Mitglied's group.

   The frozen file builds the app with recording fakes and fails on any write at start or on any request it makes.
10. **Isolation as in `identity/`:** one installation per database, no tenant column. Every statement names the role
    or person by id. A foreign or malformed id is `RoleNotFound`, exactly like a missing one. Rows are mapped by
    position, as in the rest of `identity/`.
11. **No customer text in logs** (FU-14, maintenance PR #55): ids and counts only, DEBUG included. No role name,
    description, person name or address reaches a log line or a `RoleError` message; the page writes its own words.
12. **One transaction per change** (`conn.transaction()`, which becomes a savepoint inside a caller's transaction).
13. **Names:** trimmed, white space collapsed, 1 to 80 characters, unique regardless of case.

## Decisions this order takes (draft: for the coordinator to confirm before the tests are frozen)

1. **The Core group is RB-4's** (rule 9). Design § 3 says Mitglied's group is "made by a start-up step". This order
   moves that to RB-4 on an administrator's action, because a start-up step would write to the tenant on every boot,
   and the frozen file now forbids any write at start.
2. **`admin` belongs to Administration alone** (rule 2). The design does not say so; it keeps "who is an
   administrator" in one place and gives rule 4 a single meaning.
3. **`grant_role` and `revoke_role` stay**, with the semantics of rule 8, until RB-4 replaces the people page. Later
   items keep them, because `conftest.py` uses `grant_role`.
4. **The cap is checked when written and when signed, not when read** (rule 6).
5. **Deactivating the last administrator** stays as today (only deactivating oneself is refused) until RB-4.
6. **A new account joins no role** (rule 8); "every person is a member" holds after the move and for accounts made in
   the console. The first administrator of a new installation is in Administration only.
