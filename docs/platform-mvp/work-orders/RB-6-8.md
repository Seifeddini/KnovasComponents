## Goal

An agent is a member of roles that is not a person: the Knovas Assistent, or an external agent (Claude Code, Claude
Desktop, Copilot …) an administrator registers. Every agent's request to the Core carries **one claim the Platform
signs**: the agent's id as subject, the groups and functions of the agent's roles, narrowed to what the person holds
when the agent acts for a person. External agents reach the Brain **only through the Platform**: they present a key
issued in the console to the Platform's MCP endpoint, the Platform signs their claim and calls the Core over its own
certificate (design § 5). The tenant certificate never leaves the Platform (AGB-01).

**Not in this item:** agents as members on the Rollen page (RB-4's member picker, through `AgentStore.add_to_role`);
data (RB-5); Probe (RB-9); a key renewal page; OAuth; the MCP revision 2026-07-28; tools that write; moving Claude
Code off the internal MCP server (a deployment step after this item, see "After this item").

## One builder, three commits (recommended)

One builder takes RB-6, RB-7 and RB-8 on one branch, **one commit per item** in this order:

1. `RB-6: …` the migration `0028_agents` (whole), `identity/agents.py` with the claim, the assistant as a member,
   the assistant's own claim, the actor;
2. `RB-7: …` keys, revoke, the end date, acting for a person, the console's agent pages;
3. `RB-8: …` the gateway, its settings, the audit line, the rate limit, the docs and cards.

Why not three builders: the three share one migration, one interface (`identity.agents`), one frozen file and one
verifier's read of the secret path. RB-8 cannot be tested without RB-6's claim and RB-7's keys; split, RB-7 would
need a second migration and RB-8 a stub key store, and the critical review would see the key handling twice in
pieces. 16 points (3 + 5 + 8) is a large item but one coherent diff. The frozen file goes green only at the end; the
builder's notes say which tests each commit turns green.

RB-3 and RB-4 run in parallel. The touch points are small and named under "Files you may change"
(`identity/roles.py`: two statements; `admin.py`: one attach call; the Admin page list: one entry). Whoever merges
second resolves them; the frozen RB-1/2 interface does not change.

## What to build (the frozen tests pin the interface)

### 1. Migration `P/src/identity/migrations/0028_agents.sql` (RB-6, the next number after `0027_roles`)

New tables only, header in the style of `0027_roles.sql` (plan, items, design; that it adds tables only). The frozen
file reads the names in bold and scans every table for the key.

- **`agents`**: `id` UUID PK; `name` CITEXT unique, 1 to 80 characters; `kind` `assistant` or `external`;
  `on_behalf_of` UUID → `users(id)` **`ON DELETE CASCADE`** (a person removed takes her agents along), NULL = acts on
  its own; `created_at`, `created_by`, `revoked_at`, `revoked_by`. Exactly one row of kind `assistant` (a partial
  unique index), and only an `external` agent may have `on_behalf_of` (CHECK).
- **`agent_keys`**: `id` UUID PK; **`agent_id`** → `agents` `ON DELETE CASCADE`; `prefix` TEXT unique (the key's
  first 12 characters, `kna_` + 8); `key_hash` TEXT (hex SHA-256 of the whole key); **`created_at`**, `created_by`;
  **`expires_at`** NOT NULL with `CHECK (expires_at <= created_at + interval '90 days')`; `revoked_at`;
  `last_used_at` (written at most once a minute, as `exp_api_tokens` does). Never the key, never an encrypted copy.
- **`tenant_role_agents`**: **`role_id`** → `tenant_roles` `ON DELETE CASCADE`, **`agent_id`** → `agents`
  `ON DELETE CASCADE`, `added_at`, `added_by`, both ids the key; an index on `agent_id`.
- The rate limit's counter (rule 12): columns on `agents` or a table of its own, your choice, in this file.
- The seed, in SQL: one agent `Knovas Assistent` of kind `assistant`, without a key; it joins **every role but
  Administration** (on a new installation: Mitglied; on an existing one also every role RB-1's move created).

### 2. `P/src/identity/agents.py` (the interface RB-4 and later items build on)

```python
MAX_KEY_DAYS = 90

class AgentError(Exception)             # every refusal; plain German, safe to show, no name, no key
class AgentNotFound(AgentError)         # missing, foreign or malformed id: one answer
class AgentNameTaken(AgentError)
class ProtectedAgentError(AgentError)   # revoking the assistant (it has its switch)

@dataclass(frozen=True)
class Agent:
    id: UUID; name: str
    kind: str                           # "assistant" | "external"
    on_behalf_of: UUID | None           # the person an external agent acts for, fixed when it is created
    roles: frozenset[UUID]
    key_prefix: str | None              # "kna_" + 8, for recognition; None for the assistant
    expires_at: datetime | None         # of the newest key
    revoked: bool
    # never the key, never its hash

@dataclass(frozen=True)
class NewAgent:
    agent: Agent
    key: str = field(repr=False)        # the only place the key ever exists in clear

@dataclass(frozen=True)
class AgentClaim:
    subject: str                        # str(agent.id)
    groups: tuple[str, ...]             # sorted
    functions: tuple[str, ...]          # sorted
    on_behalf_of: UUID | None

class AgentStore:
    def __init__(self, conn)
    def assistant(self) -> Agent
    def list_agents(self) -> list[Agent]                       # the assistant first, then by name
    def get_agent(self, agent_id) -> Agent
    def create_agent(self, *, name, on_behalf_of=None, days=MAX_KEY_DAYS, by=None) -> NewAgent
    def revoke_agent(self, agent_id, *, by=None) -> Agent
    def add_to_role(self, role_id, agent_id, *, by=None) -> None
    def remove_from_role(self, role_id, agent_id, *, by=None) -> None
    def roles_of_agent(self, agent_id) -> list[Role]
    def claim_for(self, agent_id, *, on_behalf_of=None) -> AgentClaim
```

Refusals about roles and groups are RB-1's: `ProtectedRoleError` (an agent and Administration) and
`TooManyGroupsError` (rule 6). How the gateway authenticates a key (a method on the store or a function) is yours;
the frozen file reaches it only through `/mcp`.

### 3. The claim (RB-6)

- `PrincipalBroker` (`identity/principal.py`) signs an agent's claim from `AgentStore.claim_for`: `sub` = the agent's
  id, `grp` = its groups, `rol` = its functions, `tid` and the lifetime as for a person (120 seconds, at most 300).
  The signer (`identity/assertion.py`) does not change; the claim has exactly today's fields.
- The client carries it the way it carries a person: `KnovasAPIClient.asserting_for(<an agent principal>)`, the
  assertion in the body field `principal_assertion` (`_with_principal`). Nothing else sets the subject.
- **The declared actor** (design § 4, the Core's `services/request_actor.py`): every request made for an agent also
  carries `actor = {"kind": "agent", "id": "<agent id>", "on_behalf_of": {"kind": "user", "id": "<person id>"} or
  null}`: in the JSON body of a `POST` (frozen on `POST /secured/query`), as `?actor=<base64url JSON>` on a `GET`
  graph read (the Core reads it there). The Core decides nothing on it; it logs the agent id in clear and the
  person's id hashed.
- **The assistant uses the same rule.** Every Core call the assistant makes while answering (the search, the
  doc-fields probe inside it, `/secured/llm/generate`) carries the **assistant's** claim, narrowed to the signed-in
  person, never the person's own claim. Wrap the whole answer, not only the search (`install_assistant` or
  `make_service`; the service and the check do not change). The wrapping must still fail closed:
  `tests/test_assistant_page_routes.py::test_the_real_service_is_wired_and_fails_closed_without_the_secured_api`
  builds the real service on a fake client without `asserting_for` and expects the plain `failed` reply, not a 500
  (the draft's reference implementation broke exactly this test; it stays green unchanged).
- `RoleStore.create_role` (RB-1) adds the assistant to the new role in the same transaction. `set_core_group` also
  checks rule 6 for the role's agents that act on their own.

### 4. Keys, revoke, the end date, acting for a person (RB-7)

- **Format:** `kna_` + 8 characters `[a-z0-9]` (with `kna_`: the 12-character prefix, unique, stored in clear, shown
  in the list) + `_` + `secrets.token_urlsafe(32)` (43 characters, 256 bits). `kna_` lets secret scanners and people
  recognise a Knovas agent key.
- **Shown once:** `create_agent` returns it in `NewAgent.key`; the page shows it in the answer to "Anlegen" and in no
  later page, response, log line, exception or audit row.
- **Stored as a hash:** hex SHA-256 of the whole key in `agent_keys.key_hash` (the keys are random, so a slow hash
  adds nothing; the same choice as `exp_api_tokens`, migration 0003). No encrypted copy.
- **Compared in constant time:** look the row up by the prefix, then `hmac.compare_digest` on the two hashes, called
  as `hmac.compare_digest` (the frozen file watches that name). Compare against a fixed dummy hash when no row has
  the prefix, so the time does not tell a known prefix from an unknown one.
- **The end date:** 1 to 90 days, default 90 (`MAX_KEY_DAYS`), checked in the store and by the table's CHECK. From
  `expires_at` on the key gets 401. No renewal in this item: an administrator creates a new agent (decision 8).
- **Revoke acts at once:** `revoke_agent` sets `revoked_at` on the agent and on all its keys in one transaction; the
  next request gets 401. There is no cache to wait for: the key is checked against the database on every request, and
  the claim the Platform signed for an earlier call is used only inside that call.
- **Acting for a person:** fixed when the agent is created; the person must exist and be active. While the person is
  not active, the agent's key gets the same 401. The assistant acts for the signed-in person and is never bound to
  one; `claim_for(assistant)` without a person is `AgentError`.
- **One 401 for every failure:** no header, another scheme, a malformed, unknown or wrong key, an expired or revoked
  key, an agent whose person is not active: the same status, the same body, the same `WWW-Authenticate: Bearer …`.
  The log line says "refused" and nothing of the key.

### 5. The gateway (RB-8)

**Transport (decided here, sources below):** MCP Streamable HTTP of revision **2025-11-25** in its smallest form.

- One endpoint, **`POST /mcp`**, blueprint `agent_gateway`, endpoint **`agent_gateway.mcp`**. Every answer to a request
  is one JSON object (`Content-Type: application/json`); no SSE, no `Mcp-Session-Id` (stateless), no batch.
- Checks in this order: the switch (`agents.enabled` off → **404** for every method, the key not even looked at);
  `GET` and `DELETE` → **405**; an `Origin` header that is present and is not the Platform's own (scheme and host of
  the request) → **403**; the key → **401** (rule 4); an `MCP-Protocol-Version` header other than `2025-11-25`,
  `2025-06-18` or `2025-03-26` → **400** (no header: 2025-03-26, as the spec says); then the body. Register the
  route for `GET` and `DELETE` too and answer 405 yourself: with `POST` alone, Flask's routing fails before the
  identity gate, which then redirects the `GET` to the sign-in page.
- Methods: `initialize` (answers the client's version if it is one of the three, else `2025-11-25`;
  `capabilities.tools`; `serverInfo`; short `instructions` in the style of today's server, without readiness),
  notifications (`notifications/initialized` …) → **202** without a body, `ping`, `tools/list`, `tools/call`;
  anything else → JSON-RPC error -32601.
- **Credential:** `Authorization: Bearer <key>` only. The gateway replaces the request's session with Flask's null
  session (as `experiments_routes._without_session` does), so the browser's cookie is never read and never sent back;
  `gate.allow_bearer_endpoints(["agent_gateway.mcp"])` lets the identity gate stand aside.
- **CSRF:** `agent_gateway.mcp` is added to `_CSRF_EXEMPT_ENDPOINTS` in `app.py`, and nothing else is exempted: the
  endpoint takes no ambient credential, so a forged browser request carries nothing to ride on, and the Origin check
  refuses a browser of another site.
- **Tools** (rule 9): `knovas_query`, `knovas_find_node`, `knovas_explain`, `knovas_neighbors`, with the names of
  today's Knovas MCP server so the `knovas` skill keeps working. Each runs inside
  `api_client.asserting_for(<the agent>)` on the app's one `KnovasAPIClient`, so the Core sees the agent's claim and
  the Platform's certificate. Every tool's `inputSchema` has `additionalProperties: false`; a call with an argument
  the tool does not offer (`access_groups`, a tenant, a client id) or a tool that is not listed is refused before the
  Core is asked. Annotations `readOnlyHint: true`.

  | Tool | Arguments | Core call (all already in `KnovasAPIClient`) | Result |
  |---|---|---|---|
  | `knovas_query` | `question` (1 to 2,000 characters), `limit` (1 to 50, default 10) | `search_plan(…, enabled=False)` + `run_search` in `keeping_snippets()`, then the search page's `split` (experiment documents never reach an agent) → `POST /secured/query` | per hit: `pointer`, `title`, `page`, `passage` |
  | `knovas_find_node` | `type` (name or id), `name` (substring), `limit` (1 to 100, default 20) | `graph_node_types`, `graph_nodes` → `GET /secured/graph/node-types`, `/nodes` | `id`, `name`, `type` |
  | `knovas_explain` | `node_id` | `GET /secured/graph/nodes/<id>/dossier` | the dossier as the Core returns it |
  | `knovas_neighbors` | `node_id`, `depth` (1 to 3, default 1) | `graph_neighbors` → `GET …/neighbors` | `neighbors`, `edges` |

  Not offered: `knovas_check_readiness` (the tenant's operational verdict: an operator's read, not a person's),
  `knovas_path`, `knovas_facts_trust`, `knovas_list_nodes` (reads every node of a type: a rate-limit and size
  question for later), `knovas_closest` (a Brain-maintenance tool), the connection tools and anything that writes.
  The Core filters every one of the four by the claim (`graph_api.py`: `_node_visible_with_type`, `_visible_facts`
  on the principal). Size cap per answer as today's server (60,000 JSON characters for `knovas_query`, lowest ranked
  cut first, `truncated: true`; not frozen). A Core failure is a tool result with `isError: true` and a fixed German
  text (429/503: "ausgelastet"), never the Core's text.
- **The audit line** (rule 11): one `audit_log` row per `tools/call` that passed the key and the rate limit, written
  with `audit.record`: `action = 'agent.call'`, `actor_user_id` NULL, `target_type = 'agent'`, `target_id` = the
  agent's id, `outcome` `ok`, `denied` (unknown tool, refused arguments, unknown node) or `error`, `detail` =
  `{"tool", "key" (the key's id), "on_behalf_of" (a person's id or null), "results" (a count), "ms", "reason" (a
  fixed code)}`, `ip`; no user agent. Plus one INFO log line with the same ids. `initialize` and `tools/list` write
  none.
- **The rate limit** (rule 12): per agent, `tools/call` only, `agents.calls_per_minute` (default 60).
- **The switch:** `agents.enabled`, independent of `assistant.enabled` (section "A client with only external agents").

## The transport and the authentication: what this order relied on

Read on 2026-11-21 on modelcontextprotocol.io and code.claude.com:

- **Revision 2025-11-25, Streamable HTTP** (`/specification/2025-11-25/basic/transports`): a request POSTed to the
  one endpoint may be answered with `Content-Type: application/json`; the server "MUST either return
  `Content-Type: text/event-stream` in response to this HTTP GET, or else return HTTP 405"; a session id is a "MAY";
  without `MCP-Protocol-Version` the server "SHOULD assume protocol version 2025-03-26", an invalid or unsupported one
  "MUST" be 400; an invalid `Origin` "MUST" be 403. A notification is answered 202 without a body.
- **Revision 2026-07-28** (`/specification/2026-07-28/basic/transports/streamable-http.md`, `…/versioning.md`) is the
  current one: no `initialize`, no sessions, the version in every request's `_meta` and in headers (`Mcp-Method`,
  `Mcp-Name`) the server must validate. Its compatibility matrix: a **legacy** server (one that answers `initialize`)
  works with legacy clients and with dual-era clients, which fall back to `initialize` after a 400 whose body is not
  a modern error; it does not work with a client that speaks only 2026-07-28.
- **Authorization, 2025-11-25** (`/specification/2025-11-25/basic/authorization`): "Authorization is OPTIONAL for MCP
  implementations"; when supported over HTTP it "SHOULD" be OAuth 2.1 with Protected Resource Metadata (RFC 9728).
  Tokens go in `Authorization: Bearer`, never in the query; invalid or expired ones get 401; a server "MUST NOT"
  pass a client's token on. The gateway never forwards the agent's key: it signs its own claim.
- **Claude Code** (`code.claude.com/docs/en/mcp`): `claude mcp add --transport http <name> <url> --header
  "Authorization: Bearer <token>"`, or `"type": "http"` with `"headers"` in `.mcp.json` (with `${VAR}` expansion);
  with an `Authorization` header configured it does not fall back to OAuth, and a 401 shows the connection as failed.

**Chosen: the 2025-11-25 era only, and a bearer agent key.** It is the smallest transport real clients use today: a
handful of JSON-RPC methods in one Flask route, no new dependency (the `mcp` package's server is ASGI; the Platform
runs Flask under gunicorn, and an adapter would be larger than the five methods). **What it costs:**

- A client that speaks only 2026-07-28 cannot connect. Adding that era later means `server/discover`, the `_meta`
  fields, the header validation and the `-32022` error; the tools and the claim stay.
- No OAuth: no sign-in flow in the client, no per-person consent, no token refresh. A client that connects to a remote
  server only through OAuth (connector dialogs of web and desktop apps) cannot use the endpoint directly. The key is a
  long-lived secret (at most 90 days) on the agent's machine; leaking it is limited by the end date, revoke, the
  rate limit, the audit line and, with "Ein", the agent's roles and person.
- **Not verified today:** whether the installed Claude Desktop and VS Code (Copilot) accept a fixed header for a remote
  server. The builder checks them against a local Platform before the pilot (Done when 4) and writes the result.

## Rules

1. **New tables only.** No change to any existing table, column, index, constraint or trigger, to any existing
   migration (0027 included), or to RB-1's interface. `identity/roles.py` changes in two places only (section 3).
2. **One claim for every agent**: `sub` = the agent's id; `grp`, `rol` = the groups and functions of its roles;
   acting for a person, intersected with `access_groups_of(person)` and `roles_of(person)`. A person's direct group
   grants do not reach an agent (only roles do; decision 4). The assistant follows the same rule for the signed-in
   person and is a member of every role but Administration, also of roles created later.
3. **No agent joins Administration** (`ProtectedRoleError`, nothing written): `admin` belongs to people (RB-1 rule 2).
4. **Keys** as section 4: shown once, a SHA-256 stored, `hmac.compare_digest`, a prefix for recognition, at most 90
   days, revoke at once, one 401 for every failure.
5. **The key never appears** in a log line (DEBUG included), an exception message or `__context__`, an audit row, a
   page after the one that created it, a response other than that one, or `repr`. Nor does its hash.
6. **32 groups** (RB-2's cap): no agent's claim carries more than `MAX_CLAIM_GROUPS`; `claim_for` raises
   `TooManyGroupsError` and nothing is sent. `add_to_role` and `set_core_group` refuse, with nothing written, when an
   agent that acts on its own would hold more. (An agent bound to a person, and the assistant, are narrowed to a
   person who holds at most 32.)
7. **Functions** do not gate the four read tools, as no function gates search for a person (design § 2.1); they ride
   in `rol` and gate tools that later items add.
8. **Through the Platform only**: the gateway calls the Core with the app's `KnovasAPIClient` (the Platform's
   certificate) and nothing else; it never forwards the agent's key, never accepts `access_groups`, a tenant or a
   client id from the agent.
9. **Tools**: exactly the four, or fewer under the cut rule (`knovas_query` stays); nothing that writes.
10. **Session and CSRF**: `/mcp` never reads or sets the session cookie; it is the only new CSRF exemption.
11. **No customer text** in an audit row or log line (FU-14, maintenance PR #55): no question, passage, pointer,
    title, node name, agent name or person name; ids, counts, fixed codes and durations only. The agent's name is the
    tenant's text, like a role's name.
12. **The rate limit** is per agent and per minute, counted in the database (gunicorn's workers share it; the in-process
    `custom_views.budget` would not), one atomic statement per call. Over it: **429** with `Retry-After` (seconds,
    at least 1), a JSON-RPC error body, nothing sent to the Core, **no audit row** (an agent cannot flood the audit
    table), one INFO log line with the agent's id. Unauthenticated requests are not counted (256-bit keys); a
    `limit_req` for `/mcp` in nginx is the deployment's (PMVP-62).
13. **Audit of changes** (design rule 4): `agent.created` (detail: the key's id, the days, `on_behalf_of`),
    `agent.revoked`, `agent.role_added`, `agent.role_removed`, written by the store in the change's own transaction,
    `actor_user_id` = `by`. Never the key or its hash; not the agent's name.
14. **Nothing is written to any tenant** by this item: no Core group, no rule, no document right. The gateway reads.
15. **One transaction per change**; ids malformed, foreign or missing are one `AgentNotFound`; rows mapped by
    position, as in the rest of `identity/`.

## The narrowing acts only with CR-R1: what the pilot gets before it lands

The Core verifies the Platform's claim only in the posture `brokered`, and no route can set it (CR-R1). Until then:

- **Aus (`disabled`, the pilot today):** every agent, like every person, reads everything the tenant holds. What acts:
  the key (shown once, hashed, 90 days, revoke at once, one 401), the switch, the Origin rule, the rate limit, the
  audit line, the tools' fixed arguments, and the tenant certificate staying on the Platform. The claim is signed and
  the Core logs the agent and the person (`actor`), but the groups do not narrow.
- **`enforcing` without CR-R1:** the Core ignores the claim and reads the body field `access_groups`, which the Platform
  never sends: every agent, like every person, sees open documents only.
- **With CR-R1 and "Ein":** every rule of this order acts as written; nothing in the Platform changes.

Compared with today: the internal MCP server reads the Knovas tenant with the tenant certificate and groups the model
chooses (design § 2.4); the gateway is never more open than that and is keyed, revocable and audited. **For a law
firm** an external agent acting for one lawyer would, before CR-R1, read the whole firm. Recommended: switch
`AGENTS_ENABLED` on for a law-firm client only once CR-R1 has landed and "Ein" is set, or with the client's written
acceptance (the founder decides, decision 10). The page says so (section 7).

## A client with only external agents and no assistant

`ASSISTANT_ENABLED=aus`, `AGENTS_ENABLED=an`: `/fragen` answers 404, `/mcp` serves external agents (frozen). Nothing
in the gateway depends on the assistant, its provider or its key (no Anthropic key needed). The assistant's row stays
in the register and in the roles (it has no key and cannot be reached); the list shows it as off. External agents
get their data through roles (RB-4's member picker) like people. The Platform must be reachable from where the agents
run (design § 5, cost); for a client whose agents run outside the firm, that is the host nginx's public name with TLS.

## Decisions this order takes (draft: for the coordinator and the founder to confirm before the tests are frozen)

1. **MCP revision 2025-11-25 only**, not 2026-07-28 (cost above).
2. **A bearer agent key, no OAuth** (cost above). The design's open point "a key per agent, sent as a header, at most
   90 days" (§ 9) is taken as recommended.
3. **Four tools with today's names**; `access_groups` gone from the schema; readiness not offered.
4. **A person's direct group grants do not reach an agent**, the assistant included: one rule, roles carry data.
   Consequence under "Ein": a person whose sight comes only from direct grants (`user_access_groups`) gets open
   documents only from the assistant until her data is on roles (RB-4, RB-5). The alternative (the assistant also
   keeps the person's direct grants) would make "take the assistant out of a role" leak through direct grants.
5. **The assistant joins every role but Administration**, also roles created later (opt-out, A-10 "may be used by
   AI"); **no agent ever joins Administration**.
6. **The assistant's claim on every Core call of an answer**, `/secured/llm/generate` included: the Core's logs show
   the assistant as subject and the person (hashed) as `on_behalf_of`, no longer the person as subject.
7. **Functions do not gate the read tools** (rule 7).
8. **Keys**: SHA-256, 90 days at most, **no renewal page** (a new agent after 90 days; its roles are set again);
   revoke takes the whole agent.
9. **The rate limit**: 60 calls a minute by default, in the database, no audit row for a 429.
10. **Before CR-R1** agents read what the posture lets everyone read; for a law firm, agents only after CR-R1 or with
    written acceptance: **the founder decides**.
11. **`AGENTS_ENABLED` is off by default**, like the assistant.
12. **`actor` in the body of `/secured/query`**: the Core on `master` reads it there (`request_actor.py`, KC-7a). Check
    that the production Core is that version before switching agents on; an older Core might refuse an unknown key.
13. **A person removed takes her agents along** (`ON DELETE CASCADE`); deactivated, they get 401.
14. **No new dependency**: the design's "new dependency `mcp`" is not needed (section "transport").
15. **One builder, three commits.**
